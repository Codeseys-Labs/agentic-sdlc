# Receipts machinery deep-read — `ccodex sdlc` install/update/uninstall/recover

Repo: `Codeseys-Labs/agentic-sdlc` (checked out at `/tmp/asdlc-research`, HEAD `e0fbf9241d4fb2a756448e856c4b5943e6a188bd`, branch `main`, `.version-bump.json` declares `0.7.4`). All line numbers below are from this checkout unless marked otherwise. Where a claim is checked against the live public repository (via the GitHub REST API and a downloaded release asset, both fetched over plain HTTPS — no `mise` command was ever invoked, per instructions), it is marked **[live-verified]**.

## Executive summary

The repo is not merely "in the direction of" the operator's proposal — it has a fully-specified, receipt-sealed, exit-code-disciplined install/update/uninstall/recover lifecycle for a *release payload*, built as five cooperating scripts (`scripts/ccodex_sdlc.py` + four per-verb siblings) plus two receipt-schema modules (`scripts/write_acquisition_receipt.py`, `scripts/distribution_activation_receipt.py`). It has been proven end-to-end in a disposable container against a real, deterministically-built candidate (`docs/evidence/waves/f194-w1/journey.md`). **[live-verified]** Two real GitHub prereleases (`v0.7.3`, `v0.7.4`) exist today, each a `build_release.py` "git-archive-of-tracked-files" tarball with a `manifest.json`, installable via `mise use -g github:Codeseys-Labs/agentic-sdlc --prerelease` (exact-version only).

However, **the one thing that is actually shipping and working against that real GitHub artifact today is the *other*, receipt-less installer (`ccodex bundle install`), not the receipts machinery.** I found and independently confirmed (byte-diffing the live release tarball against `main`, plus a same-day, already-closed seed) that the published `v0.7.4`/`v0.7.3` release's dispatcher routes `ccodex sdlc *` through `uv run --script` (no `-I`/`-B`), which the reader's own `runtime_admission()` in `scripts/ccodex_sdlc.py:454-471` refuses by name — so **every `ccodex sdlc` verb, including `install --host claude`, currently exits 3 ("expected direct -I -B execution") when run from the actual downloaded release artifact.** The fix (`main@cd3fd3d`, seed `agentic-sdlc-dca4`, closed 2026-08-24) is on `main` but has not been re-released under a new tag as of this checkout. So: the receipts machinery is real, deep, and tested — but not, as of this exact commit, the path that works against the one artifact an operator can download from GitHub right now.

The machinery also covers only user-scope `~/.claude` activation on Linux x86_64; there is no project-scope `.claude` support anywhere in the underlying primitive (`install_skill_bundle.agent_root` always resolves to `config.home / ".claude"`), no rollback/downgrade verb (only resume/abort of one interrupted transaction), and the "acquire a release from GitHub" leg is itself split between a real, working `mise`+GitHub-releases mechanism and a still-manual "placement bridge" script that `write_acquisition_receipt.py` requires.

### The five-phase chain, exactly as the code implements it

1. **Build a candidate** — `scripts/build_release.py:build()` (`scripts/build_release.py:202-287`). `git archive` over the exact clean `HEAD` commit, allow-listed to `policy/release-candidate.v1.json`'s `payload.files`/`payload.trees` (`policy/release-candidate.v1.json:1`). Appends a `manifest.json` (per-file sha256, per-symlink target, `source.commit`/`source.tree`, `candidate_id` = sha256 of the whole inventory). No interpreter or runtime dependency is bundled (`scripts/build_release.py:28-29`, "No interpreter is bundled"). Output: `dist/agentic-sdlc-<version>.tar.gz` + `dist/SHA256SUMS`.

2. **Acquire → seal an acquisition receipt** — `scripts/write_acquisition_receipt.py:write_receipt()` (`scripts/write_acquisition_receipt.py:222-301`). Given `--root <candidate-root> --state-home <xdg-state-home> --archive|--archive-sha256`, it **re-hashes every entry** in the candidate root against the root's own `manifest.json` in both directions (`verify_root`, `scripts/write_acquisition_receipt.py:139-198`), then seals a `release-candidate-acquisition-receipt/v1` document create-only (`O_EXCL`+`O_NOFOLLOW`, fsynced, read back and compared, `scripts/write_acquisition_receipt.py:271-300`) under `$XDG_STATE_HOME/agentic-sdlc/acquisition/receipts/<archive-sha256>.json`. The receipt's constants are fixed at seal time (`RECEIPT_CONSTANTS`, `scripts/write_acquisition_receipt.py:83-92`):
   - `terminal_phase: "installed-unselected"` — the receipt's **one and only** terminal state; nothing in the codebase ever transitions it further.
   - `selection: "absent"` — always. There is no code path anywhere in this tree that ever writes any other value into this field. "Selection" (i.e. picking among several acquired candidates, e.g. by channel) is vocabulary that exists in the schema but has **no producer that ever exercises it**.
   - `activation: "absent"` — always, inside the acquisition receipt's own seal; this is distinct from the separate *activation plane* (item 4 below), which is a different set of documents entirely.
   - `public_channel: null`, `release_claim: "none"`, `support: "unsupported"` — the acquisition receipt itself never claims a release exists.
   This tool is **never invoked by any of the four `ccodex_sdlc_*.py` lifecycle modules**; grep across the whole tree shows its only callers are the docs (`docs/plans/2026-08-14T163833Z-Install-UX.md:208-210`), the tests, and the container journey script (`docs/evidence/waves/f194-w1/journey-track.sh`). It is a human/CI-run bridging tool, not a wired verb (see §b).

3. **Admit → check compatibility → copy-activate** — `scripts/ccodex_sdlc_install.py:run_install()` (`scripts/ccodex_sdlc_install.py:1771-1917`), same shape reused (with a mandatory-different-identity twist) by `scripts/ccodex_sdlc_update.py`:
   - **Admit exactly one** acquisition receipt: `admit_acquisition_receipt` (`scripts/ccodex_sdlc_install.py:631-665`) refuses an absent, empty, or ambiguous (>1 receipt) acquisition-receipts directory by name; there is no `--from`, no discovery, no wildcard (module docstring, `scripts/ccodex_sdlc_install.py:22-30`). The receipt's own seal is re-derived (`acquisition_record_digest`, `scripts/ccodex_sdlc_install.py:667-679`) and every constant field is re-checked (`validate_acquisition_receipt`, `scripts/ccodex_sdlc_install.py:681-735`), including `terminal_phase == "installed-unselected"` and `selection == "absent"`.
   - **Check compatibility**: `check_compatibility` (`scripts/ccodex_sdlc_install.py:938-1009`) reads the *payload's own* `policy/release-contract.v1.json` (not the reader's), confirms `compatibility.core.host == "claude-code"`, observes the live `claude --version` (`observe_host_version`, `scripts/ccodex_sdlc_install.py:885-913`, subprocess with a 20s timeout), and refuses by name on: wrong host in the contract, an unobservable host version, a version present in `known_incompatible_host_versions`, or a version below `minimum_host_version`. It **never substitutes a requested/nominated version for the observed one** (this exact anti-pattern is cited by seed id, `scripts/ccodex_sdlc_install.py:34-37`).
   - **Copy-activate**: `classify_entries` (`scripts/ccodex_sdlc_install.py:1134-1205`) classifies every Claude-host entry the payload carries as `absent`/`owned`/`foreign`/`modified` **before any write**, reusing `install_skill_bundle.destination_for`/`assert_safe_collection`/`agent_root`. `foreign` and `modified` entries are preserved and named, never adopted or overwritten (no wildcard, no `--all`, no purge). `activate()` (`scripts/ccodex_sdlc_install.py:1492-1554`) then runs each planned entry through `install_skill_bundle`'s own crash-consistent `transactional_create`/`transactional_replace`, stopping at the first failure.

4. **Seal a distribution-activation receipt, then point the plane at it** — `build_receipt_body`/`seal_receipt` (`scripts/ccodex_sdlc_install.py:1634-1718`) build a `distribution-activation-body@1` document (schema and vocab owned by `scripts/distribution_activation_receipt.py:1-198`) recording `operation`, `host`, `activation_scope` (`"claude-home"`), `resolved_version` (from the *candidate's own manifest*, never from a request — `version_source: "archive-manifest"`), the full per-entry inventory with `prestate`/`disposition`/`content_sha256`, `effect_state`, `terminal_phase`, and exactly one `derived-from` ancestor naming the acquisition receipt's `operation_id`. `effect_state`/`terminal_phase` are derived from the receipt family's own closed matrices (`EFFECT_PHASES`, `OPERATION_PHASES`; `scripts/distribution_activation_receipt.py:1242-1255`), never invented locally. The receipt is written create-only and durably (`write_new_document`), and **only then** is `activation/active-receipt.json` replaced atomically (`replace_active_pointer`, `scripts/ccodex_sdlc_install.py:1730-1752`) — receipt-then-pointer, never the reverse, so there is no window where the pointer names a document that doesn't exist. Exit 0 requires all three: every claimed effect complete, the receipt sealed, and the pointer moved (`scripts/ccodex_sdlc_install.py:1905-1917`).

### What "installed-unselected", "selection", and "activation" mean, precisely

- **`installed-unselected`** (acquisition receipt `terminal_phase`): the payload has been placed on disk and its bytes verified against its own manifest — that's "installed" in the sense of "present and verified" — but it has not yet been chosen to run anywhere. It's a dead-end state in the current code: nothing ever moves a receipt out of it.
- **`selection`** (acquisition receipt field, always `"absent"`): scaffolding for a not-yet-built step where, if multiple acquired candidates existed (e.g. two channels or two versions), one would be marked selected. `ccodex sdlc install`/`update` implement selection *implicitly* by refusing ambiguity (exactly one admissible acquisition receipt must exist, or exactly one whose identity differs from the currently-active one for `update`) rather than by writing anything into this field.
- **`activation`** — two unrelated meanings coexist in this codebase and are easy to conflate:
  1. **Distribution activation** (this document's subject): the host-level act of copying a verified acquisition payload's Claude-host entries into `~/.claude` and sealing a `distribution-activation@1` receipt, tracked under `$XDG_STATE_HOME/agentic-sdlc/activation/{receipts,active-receipt.json}` and read by `ccodex sdlc status|inspect|doctor`.
  2. **Repository activation** (ADR-0022's original subject: `.agentic-sdlc/repo.toml`, a machine-local activation receipt binding a specific *cloned repository* to an approved setup plan). This second concept was **deleted** by ADR-0022's 2026-08-22 amendment (`docs/adr/0022-activate-repositories-through-digest-approved-plans.md:90-156`) — "the machine-local receipt (item 3) never had a reader… 70 records in 151 orphan directories… no tool, task, gate, hook, CI job, or skill ever read one back" — and replaced by a much smaller `classify`/`apply` pair in `skills/agentic-sdlc/tools/instruction-generator.py`. **This second "activation" is unrelated to the receipts machinery in this report and no longer exists as transactional machinery.** Anyone reading "activation" in this repo's ADRs must check which of the two is meant; ADR-0021 (distribution) and ADR-0022 (repository, now mostly deleted) both use the word for genuinely different systems.

### `update` and `uninstall`, in relation to `install`

- **`update`** (`scripts/ccodex_sdlc_update.py`, docstring `1-109`): admits the current `active-receipt.json` (must describe a *live* activation: `terminal_phase` in `("activated","activated-partial")`, `operation` in `("install","update")`) **and** exactly one *other* acquisition receipt whose identity differs from the one the active receipt already activated — an ambiguous "other" set refuses. Unlike `install`, a `modified` or `foreign` entry **blocks the whole run before anything moves** (`scripts/ccodex_sdlc_update.py:36-42`, `BLOCK_SENTENCE` at `:229`) — there is deliberately no partial-update class. An entry the new payload no longer carries is **preserved and named**, never deleted (`update` cannot record a `removed` disposition at all — that belongs only to `uninstall`). The prior receipt is retained under its own id (never overwritten) and the new receipt is filed before the pointer moves, in the same order as `install`.
- **`uninstall`** (`scripts/ccodex_sdlc_uninstall.py`, docstring `1-86`): the *only* candidate set for removal is the active receipt's own entry inventory — no directory listing, no wildcard. An entry is removed only if its recorded `prestate` was `absent`/`owned` **and** its live content digest still matches the receipt's recorded digest (both conditions independently load-bearing, `scripts/ccodex_sdlc_uninstall.py:20-33`). It also retires the matching ownership rows in `install_skill_bundle`'s shared `state.json` through that module's own crash-consistent pending-slot machinery, specifically because an earlier run (`agentic-sdlc-42ec`, see §c) found that skipping this left `status` reporting a contradiction the very next read.

### `recover`

`scripts/ccodex_sdlc_recover.py` is **not** a rollback-to-a-prior-version mechanism. It resumes or aborts **one interrupted transaction** — the single `pending` slot each of the two reused substrates (`install_skill_bundle`, `install_operator_tools`) can carry — via each substrate's own `recover_pending` (`scripts/install_skill_bundle.py:1123`, `scripts/install_operator_tools.py:514`). "The approval IS the digest": `--dry-run` derives a canonical plan from live journal/receipt state and renders its sha256; `--apply <digest>` **re-derives the same plan from current state** and refuses if the digest differs ("the state moved after the approval, or the approval is stale", `scripts/ccodex_sdlc_recover.py:847-853`). There is no version parameter to `recover`, and no `rollback`/`downgrade` verb exists anywhere in `ccodex_sdlc.py`'s grammar (`LIFECYCLE_VERBS = {"install","update","uninstall"}`, `scripts/ccodex_sdlc.py:46-50`); a "rollback" in the ADR-0021 sense would in practice mean re-running `update` while an older acquisition receipt happens to still be the sole non-active one sitting in the acquisition-receipts directory — there is no explicit version-targeting UI for it.

## (c) Overlap with `install_skill_bundle.py` — two installers, one repo

**Who owns what, concretely, via the `bin/ccodex` dispatcher (`bin/ccodex:287-295, 314-320`):**

```
ccodex bundle install|status|uninstall  →  run_python install_skill_bundle.py "$verb" "$@"
ccodex sdlc install|update|uninstall|…  →  run_sdlc_python "$@"  →  scripts/ccodex_sdlc.py …
```

These are **two live, independently reachable front doors in the same shipped binary**, not a deprecated-vs-current pair:

- `install_skill_bundle.py` owns the actual host-plane mutation primitives: the ownership `state.json` schema, the transactional create/replace/delete protocol, the digest/equivalence rules, the installer lock, and its own `main()` CLI (`scripts/install_skill_bundle.py:1812`), plus `mise run bundle:install -- --agent claude` (checkout-plane) and the `install-skill-bundle.sh`/`validate-bundle.sh` wrapper scripts.
- Every one of `ccodex_sdlc_install.py`, `_update.py`, `_uninstall.py`, `_recover.py` explicitly states "REUSE, NOT REIMPLEMENTATION" (e.g. `scripts/ccodex_sdlc_install.py:70-76`): they sibling-load `install_skill_bundle` and call its `discover_entries`/`destination_for`/`transactional_create`/`transactional_replace`/`load_config_state`/`installer_lock` etc. **They add three things `install_skill_bundle` itself has none of**: (1) acquisition-receipt admission (so the payload being activated is a verified, sealed candidate, not "whatever this checkout currently contains"), (2) the release-contract host-compatibility check, and (3) the distribution-activation receipt + `active-receipt.json` pointer that `ccodex sdlc status/inspect/doctor` reads.
- Both front doors **write into the same shared ownership ledger** — `$XDG_STATE_HOME/agentic-sdlc-installer/state.json` (`install_skill_bundle.py:128-130`) — so there is no file-level collision between them; an entry installed by one is a legitimate `owned` prestate the other recognizes.
- But **only the `ccodex sdlc *` family ever writes to the acquisition/activation receipt planes.** An operator who only ever runs `ccodex bundle install` has a perfectly healthy `bundle` projection in `ccodex sdlc status` (it reads the same `state.json`), but the `activation` readiness dimension will show no receipts at all — the receipt trail the operator's proposal cares about ("did this host activate from a sealed, verified artifact?") is simply silent for that install.

**Is the intent that the receipts machinery *replaces* the bundle installer?** The evidence says **not yet, and as of today it is arguably the reverse in practice.** The project's own seed record for the dispatcher bug states the fork explicitly as one of two considered resolutions: *"Decide once: teach `bin/ccodex` the isolated exec … or **document the split (bundle install is the quick-install activation route — proven working; sdlc copy-activation is operator-tools-plane)**"* (`.seeds/issues.jsonl:201`, seed `agentic-sdlc-dca4`). They chose to fix the dispatcher rather than formalize the split — but that fix is unreleased (§b), so **right now, against the one real downloadable artifact, `ccodex bundle install --agent claude` is the proven-working route and `ccodex sdlc install --host claude` is not** (AGENTS.md's own current install instructions, `AGENTS.md:193-209`, name `ccodex bundle install --agent claude`, not the `sdlc` verb, as what was proven against the quick-install tree). No design document declares `install_skill_bundle`'s standalone CLI deprecated; `README.md:587` still documents `ccodex bundle install|status|uninstall` as a first-class command table row. The receipts machinery is best described today as an **additional, stricter, evidence-producing layer that wraps the same substrate**, not a replacement — and the dispatcher bug shows the wrapping is not yet load-bearing on the one channel (real GitHub release) the operator's proposal is about.

## (d) Exit-code / authorization discipline, and what it implies for a compiled binary

**The contract.** All four lifecycle modules plus the reader implement the same repo-wide rule, "Implementation Decision 9" (verbatim, `docs/plans/decision9-conformance-survey.md:21-24`, quoting `docs/plans/claude-code-first-harness/agentic-sdlc-product-spec.md`):

> 0 for a valid query or closed requested result; 1 for unexpected internal failure; 2 for grammar/schema/input error; 3 for clean refusal before effect; 4 after an admitted partial or unknown effect.

Concretely: `ccodex_sdlc.py:parse_command` returns exit 2 on grammar errors (`:389-426`); its own reader path returns 1 on `ReportInvariantError`/`OSError`/`ValueError` (`:1810-1812`); every mutating module defines `EXIT_OK=0`, `EXIT_REFUSED=3` ("declined BEFORE any effect could occur"), `EXIT_UNKNOWN=4` ("an effect was admitted and no absence of effect may be claimed") — `uninstall`/`recover` additionally spell a same-valued `EXIT_PARTIAL=4` because Decision 9 has *one* class for both admitted-partial and admitted-unknown effects, and both modules record having shipped `1` for this in one prior release by mistake before converging (`scripts/ccodex_sdlc_uninstall.py:107-114`, `scripts/ccodex_sdlc_recover.py:47-53`, both citing seed `agentic-sdlc-d7b3`). The single fact that decides 3-vs-4 in every module is a mutable `Run.effect_started`/`ledger["moved"]` flag, checked at the moment of any exception, never the exception's *type* (e.g. `ccodex_sdlc_install.py:1969-1995`).

**Digest-gated `--apply`.** The only digest-gated mutating form in the whole grammar is `ccodex sdlc recover --apply <plan-sha256>` (`ccodex_sdlc.py:363-386, 411-421`). "The approval IS the digest": the *same* `derive_plan` function is used to render the dry-run digest and to re-derive the plan at apply time; a mismatch (state moved, or a stale approval) is refused by name before touching anything (`ccodex_sdlc_recover.py:826-853`). This pattern is a direct, smaller-scope descendant of the "approve-and-write in one invocation" design ADR-0022's 2026-08-22 amendment converged on after deleting a much larger two-invocation plan-digest engine (`docs/adr/0022-…md:90-121`) — the project has already tried, and walked back from, a heavier version of this exact idea once.

**What this implies for wrapping the machinery in a compiled binary:**

1. **The runtime-admission check is the load-bearing constraint, and it is exact-version, exact-flag.** `ccodex_sdlc.py:runtime_admission()` (`:454-471`) requires `sys.version_info[:3] == (3,12,11)` **and** `sys.flags.isolated`/`no_user_site`/`dont_write_bytecode` all true — i.e., the process must have been started as `python3.12.11 -I -B <script>`. This is not a soft preference; it is enforced on every mutating verb too (`dispatch_lifecycle`, `ccodex_sdlc.py:536-539`, re-checks it before even loading the per-verb module). A compiled binary (PyInstaller/Nuitka/a rewrite in another language) that does not reproduce *both* the exact CPython patch version and the exact isolation flags will be refused outright at exit 3 by design — this is the precise failure mode independently confirmed against the live `v0.7.4` release in §b, caused by a dispatcher that satisfied neither.
2. **Sibling-loading by absolute, non-symlink file path is the module-boundary mechanism, not a convention.** Every hand-off (`ccodex_sdlc.py:load_lifecycle_module`, `:487-520`; `ccodex_sdlc_install.py`'s `load_sibling`, `:425-453`; the read-only guard's `load_sibling`, `ccodex_sdlc_readonly.py:166-178`) uses `importlib.util.spec_from_file_location` against `Path(__file__).with_name(...)`, explicitly refusing a symlink and never touching `sys.path`. A frozen/bundled single-file binary either has to preserve this exact multi-file, on-disk-sibling layout inside its extraction directory (defeating much of the point of "compiling"), or the sibling-refusal-by-absence behavior — a distribution that ships the reader without a given per-verb module gets a clean, named exit-3 refusal rather than a crash (`ccodex_sdlc.py:504-508`) — has to be reimplemented deliberately, because a monolithic binary can't be "missing a file" the way a stripped source tree can.
3. **The read-only/mutator separation is enforced by CPython stdlib monkey-patching, not a process boundary.** `ccodex_sdlc_readonly.py:install()` replaces `os.open`, `builtins.open`, `subprocess.*`, `shutil.*`, `Path.write_*`, etc. at the module-object level. This technique has no equivalent in a compiled, non-CPython runtime; a compiled rewrite of the reader would need a different enforcement mechanism (a real OS sandbox, a separate unprivileged process, a capability system) to keep the same guarantee ("the reader acquires no writer authority", stated as the design's own claim, `ccodex_sdlc_readonly.py:1-8`).
4. **Digest re-derivation at `recover --apply` time assumes the plan-derivation *algorithm* is identical between the dry-run and the apply invocation.** The design already treats any change in derived-plan bytes as a stale approval and refuses (§ above) — which is actually *safe* under a binary upgrade between the two calls (an old approval against new code just fails to match and is rejected), but it means an operator cannot approve a `--dry-run` digest from one binary build and expect it to `--apply` cleanly under a different build unless the plan-derivation logic is byte-identical; this is a correctness feature, not a gap, but it is a constraint a binary-update flow must not silently violate (e.g., by rewriting timestamps into the plan).
5. **The Linux-x86_64 platform gate is duplicated, not centralized**, across `ccodex_sdlc_install.py:219-220`, `_update.py:205-206`, `_uninstall.py:129` (spelled differently: `SUPPORTED_PLATFORM` singular vs. the `SUPPORTED_SYSTEM`+`SUPPORTED_MACHINES` pair elsewhere), and `_recover.py:69-70`. Any cross-platform compiled-binary effort has at least four separate literal gates to find and update consistently, with no single source of truth today.

## (e) Net assessment

**How much of the operator's proposal is already built:** most of the *hard, receipt-and-transaction* part is built and has been proven once, end-to-end, in a real container run: deterministic build → sealed acquisition receipt with re-hashed evidence → host-compatibility check against a payload-carried contract → transactional, foreign-state-preserving copy-activation → sealed distribution-activation receipt with a proper ancestor/pointer/retention model → receipt-directed, digest-verified uninstall → digest-gated resume/abort of one interrupted transaction. The exit-code discipline (0/1/2/3/4) is applied consistently and is itself the subject of a repo-wide conformance audit (`docs/plans/decision9-conformance-survey.md`). **[live-verified]** Real, checksummed GitHub prerelease artifacts of the exact shape ADR-0021/Install-UX describe (source-tree tarball + `manifest.json`, `bin/ccodex` as the sole exposed command, `mise.toml`/`mise.lock` shipped so runtime tools resolve on the target machine rather than being embedded) exist and are independently downloadable today.

**The specific gaps that remain, in priority order:**

1. **The dispatcher regression makes the receipts machinery non-functional against the one artifact that actually exists on GitHub right now.** This is not a design gap but an operational one — and it is the most concrete, immediately actionable finding in this report: cut a new release (or re-tag) once `main@cd3fd3d` is included, or the "sealed release artifact" story is currently only true for the checkout-plane / placement-bridge path, not the GitHub-download path.
2. **No project-scope `.claude` install.** Structurally absent, not partially built — `install_skill_bundle.agent_root` never looks at a working directory or takes a target argument.
3. **No automated GitHub-download → acquisition-receipt bridge.** The acquisition-receipt producer exists and is well-built, but nothing wires "the archive `mise` just downloaded" to `write_acquisition_receipt.py`'s `--root`/`--archive` arguments; today that is a documented manual shell recipe explicitly labeled temporary.
4. **No rollback/downgrade/channel-switch verb**, despite ADR-0021 promising one; `recover` is transaction-resume only.
5. **Two coexisting installers with divergent evidence trails.** `ccodex bundle install` and `ccodex sdlc install` both mutate the same ownership ledger but only the latter produces the acquisition/activation receipts the operator's proposal is presumably about; the project has explicitly considered, and not yet decided against, formalizing this split rather than converging it.
6. **`policy/ccodex-sdlc-read-report.v2.json` is unused scaffolding** for a materially larger, "published release" report shape; a stray comment in `validate_bundle.py` currently overstates that it's already consumed.
7. **Known reader-consistency defect after uninstall** (`FINDING-1`, `owned-entry-conflict`/`degraded` immediately after a clean, receipted retirement) is filed but not fixed.
8. **Linux-x86_64-only, with the platform gate duplicated across four files** — no macOS/Windows story for this machinery at all yet, matching the project's own stated intent to certify Linux/WSL first.

None of the above looked, on inspection, like abandoned or fake work — the project's own evidence discipline (container journeys with committed transcripts, digest chains, a same-day seed-and-fix cycle for the dispatcher bug, an explicit conformance survey for the exit-code contract) is unusually rigorous for a pre-1.0 tool, and the ADR history shows a repeated, healthy pattern of building something elaborate (ADR-0022's original transaction engine, ADR-0025's planning compiler) and then *deleting* it once evidence showed it had no reader — which is useful context for weighing how durable any of the "proposed"/"unsupported" scaffolding noted above (the `v2` report schema, the `selection`/channel fields) is likely to be if left untouched.
