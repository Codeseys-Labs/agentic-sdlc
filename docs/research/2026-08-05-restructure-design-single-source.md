## 1. Hyperresearch inventory (local rendered artifacts)

**Structure verified:** 17 skill dirs (`hyperresearch`, `hyperresearch-1-decompose` … `hyperresearch-16-readability-audit`) under `~/.claude/skills/`, and **14** agent files at `~/.claude/agents/hyperresearch-*.md` (the brief said ~12; actual count is 14: corpus-critic, depth-critic, depth-investigator, dialectic-critic, draft-orchestrator, fetcher, instruction-critic, loci-analyst, patcher, polish-auditor, readability-recommender, source-analyst, synthesizer, width-critic).

**Provenance:** PyPI package `hyperresearch` — author "Jordan Gibbs <the package author>", **License: MIT**, homepage/repo `https://github.com/jordan-gibbs/hyperresearch`. The locally installed CLI is `hyperresearch v0.8.5` (`~/.local/bin/hyperresearch`); PyPI's latest is 0.10.0 — real version drift between what generated these files and current upstream. (A same-named but unrelated `dwstevens/hyperresearch` repo exists on GitHub — different author, different feature set (no 16-step pipeline, has Cursor/Codex/Gemini hooks) — do not conflate; the vendored files here map to `jordan-gibbs/hyperresearch`.)

**Not self-contained / confirmed not vendorable as static files (reinforces and extends the existing memo's item 17):**
- The rendered SKILL.md/agent files are **install-time output of the `hyperresearch` CLI**, not source-of-truth text. The entry skill's own bootstrap (`hyperresearch/SKILL.md` lines 78–81) instructs: if `.claude/skills/hyperresearch-1-decompose/SKILL.md` doesn't exist, run `hyperresearch install --steps-only . --json` to (re)generate it — i.e., these files are meant to be regenerated per-install, not hand-copied.
- Confirmed unresolved Jinja/template placeholders survive in the rendered output on disk: literal `{{paste research/query-<vault_tag>.md body}}` in multiple step skills (e.g. `hyperresearch-15-polish/SKILL.md:48`, `hyperresearch-14-patcher/SKILL.md:73`, `hyperresearch-5-depth-investigation/SKILL.md:39`), literal `{hpr_path}` in `hyperresearch-8-corpus-critic/SKILL.md:39`, and raw `{{ }}` blocks in `hyperresearch-instruction-critic.md`, `hyperresearch-corpus-critic.md`, `hyperresearch-readability-recommender.md`. Snapshotting these into the bundle would ship broken/unresolved template syntax, not a working skill.
- **Static model pins, confirmed and would fail this repo's own gate if vendored as agents:** every one of the 14 agent files carries a literal `model:` frontmatter key — `sonnet` (fetcher, loci-analyst, corpus-critic, source-analyst, depth-investigator) or `opus` (depth-critic, width-critic, synthesizer, instruction-critic, draft-orchestrator, readability-recommender, dialectic-critic, patcher, polish-auditor). This is exactly what `scripts/validate_bundle.py:1065` (`static model is forbidden`) rejects for `agents/claude/*.md` — but **only for agents**, not skills (see gate gap below).
- **Zero license/provenance headers in the rendered files themselves.** No copyright, no SPDX, no author string appears anywhere in the 17 SKILL.md or 14 agent .md files — confirmed by grep. The MIT license and authorship live only in the upstream PyPI/GitHub metadata, not in what's on disk. Vendoring these files verbatim without adding that provenance would violate MIT's attribution requirement invisibly.
- **External tool dependency:** every step skill assumes a live `hyperresearch` CLI/vault (`$HPR search`, `hyperresearch vault-tag`, `hyperresearch init`, SQLite index at `.hyperresearch/`). Not degradable to a no-CLI fallback; the pipeline is inert without the pinned external binary. `pipx`/`uv tool` cannot be checksum-pinned under this repo's `mise.lock` doctrine per the existing memo's item 18 — reconfirmed, no new evidence contradicts it.

**Verdict: do not vendor hyperresearch's rendered skills/agents.** This confirms and slightly sharpens the existing memo's row 17/19 verdict — three independent blockers (Jinja artifacts, static model pins, external CLI dependency) plus a fourth newly found here (zero in-file provenance). If hyperresearch is ever wanted, the correct integration is "document it as an optional host-provided capability" (as `agents/claude/sdlc-researcher.md:48-50` already does), never a snapshot of its generated files.

## 4. The plugin-install-alongside-global-install design question (part a of the user's goal) — resolved with new evidence

Executed against a throwaway `HOME=/tmp/plugin-home-test` (now deleted):

```
claude plugin marketplace add "$(pwd)"    # local path, absolute
claude plugin install agentic-sdlc@agentic-sdlc
claude plugin list
```

**Result: succeeded cleanly.** `claude plugin list` reported `agentic-sdlc@agentic-sdlc — Version 0.7.2 — Scope: user — Status: enabled`. This is new evidence beyond fact 7/8: a **local-path marketplace source works today**, contradicting nothing in fact 7 (fact 7 is about the *committed* `marketplace.json`'s `"source": "./"` being non-fetchable *remotely*; a `claude plugin marketplace add <absolute-local-path>` is a separate, working code path that doesn't go through that manifest field at all — it's the CLI resolving a directory source directly).

**What actually got installed, verified by listing the plugin cache directory and asking a fresh `claude --print` session what it could see:**
- All 12 skills loaded correctly, namespaced `agentic-sdlc:<name>` (e.g. `agentic-sdlc:sdlc-init`, `agentic-sdlc:agentic-sdlc`, `agentic-sdlc:model-tier-rightsizing`).
- **7 of the 7 Claude agents loaded**, namespaced `agentic-sdlc:claude:sdlc-*` — even though `.claude-plugin/plugin.json` declares **only** `"skills": "./skills/"` and says nothing about `agents` or `commands`. This confirms the docs' "auto-discovery of default directories always runs regardless of the manifest's declared component paths" behavior: `agents/` and `commands/` at plugin root are scanned automatically even when the manifest is silent about them, and manifest `agents`/`commands`/`skills` fields only *add* custom paths, never *replace* the defaults (verified against the official plugin-structure skill's own text: "Custom paths supplement defaults—they don't replace them").
- **A false positive/noise item:** `agents/codex/research/README.md` (a plain README, no frontmatter) was picked up and listed as an 8th "agent" by the test session, described as "looks like a README file picked up as an agent definition rather than a real agent." This is the exact same file flagged by fact 6's `claude plugin validate --strict` warning (`agents/codex/research/README.md: No frontmatter block found`) — now confirmed to have a second, worse consequence: **it silently becomes a broken pseudo-agent at runtime**, not just a validator warning. This raises the priority of fixing that file (either give it real frontmatter or move it out of any `agents/` tree that plugin auto-discovery scans) above where the memo currently ranks it.
- **Commands did NOT surface as slash-commands in the quick smoke-test** (the test only asked about skills/agents, not commands, so this is inconclusive rather than a negative finding — worth a follow-up check, but the on-disk plugin cache did contain `commands/sdlc-{init,frame,wave,mission}.md` verbatim, so the files at least propagated).
- **No hooks or MCP were exercised** because the repo ships neither today (reconfirms fact 2 exactly — `fd -t d hooks .` and `fd '\.mcp\.json' .` both returned empty at repo root).
- `settings.json` written by the install was minimal: `extraKnownMarketplaces` (recording the directory source) + `enabledPlugins`. No project-level Claude settings were touched (correct — this was a `scope: user` install).

**Resolving the "in addition to" tension (fact 5) — concrete recommendation:**
The blocking function is `marketplace_overlap()` in `scripts/install_skill_bundle.py:1447-1463`. It checks `~/.claude/plugins/{marketplaces,cache}/{agentic-sdlc,agentic-sdlc-orchestrator}` and greps `installed_plugins.json`/`known_marketplaces.json` for those two names, and if found, the direct Claude-plane install is skipped (not blocked outright — re-read the call sites at `:1346`/`:2613` before finalizing wording; the memo's fact 5 says "blocks," verify whether it's skip-with-warning or hard error before writing the exact new copy). Given the user now explicitly wants both:
- The **cleanest fix consistent with existing doctrine** is to stop treating plugin-overlap as mutually exclusive with the symlink install, and instead make the two install *the same underlying files by different mechanism* — i.e., keep the symlink installer as the Codex/Gemini/OpenCode-serving authoritative plane (per `AGENTS.md`'s existing router language), and treat the Claude plugin path purely as an *additional*, independent distribution channel for Claude specifically, which is exactly what plugins already are (they read the same `skills/`, `agents/claude/`, `commands/` trees directly off the git working tree — confirmed by the plugin cache literally containing a full copy of the repo, including `scripts/`, `tests/`, `mise.toml`, etc., because `"source": "./"` in a local marketplace entry copies the whole plugin root).
- The existing `AGENTS.md` line **"For Claude, use either direct install or the marketplace, never both"** should be narrowed, not removed: it should still forbid running `install_skill_bundle.py`'s Claude-plane symlink step *and* having the plugin enabled *for the exact same skill/agent names* (to avoid two competing definitions of e.g. `sdlc-init` visible to one session) — but the user's actual request ("plugin install IN ADDITION TO global/direct install") is answerable by **scoping the plugin to Claude only and the symlink installer to non-Claude hosts**, which the router language in `AGENTS.md` already gestures at ("Codex, Gemini CLI, OpenCode... read this file as the router"). Concretely: gate `marketplace_overlap()`'s skip behavior so it only fires for the **Claude** install target specifically (it appears to already do this per fact 5's description — "blocks only Claude" — so the mechanism may already be correct; what's missing is the *messaging/README* clarity that plugin-for-Claude + symlink-for-other-hosts is the sanctioned "both" the user is asking for, not literal double-install of Claude by both mechanisms).

**Hooks/MCP the symlink installer structurally cannot add (reconfirms fact 4, now with a concrete worked local example instead of just citing other plugins):** since the plugin cache is a literal copy of the repo root, adding `hooks/hooks.json` and/or `.mcp.json` at the repo root would flow through the *already-working* plugin install path with zero additional plumbing — verified structurally (the installed cache included every root-level file/dir from the repo, including ones with no explicit manifest entry, e.g. `.github/`, `docs/`, `SESSION-HANDOFF.md`). The only work needed to ship hooks/MCP via the plugin is: (1) write `hooks/hooks.json` and/or `.mcp.json` at repo root using `${CLAUDE_PLUGIN_ROOT}`-relative paths per the official pattern, (2) decide what they should do (git-destructive-op guardrail per the memo's backlog #13 is the most concretely justified candidate found in this session's evidence), (3) keep them Claude-plugin-only, never claimed as a symlink-installer capability, matching this repo's own host-agnostic doctrine (hooks are a Claude Code-specific primitive with no AGENTS.md-host equivalent).

## 5. Automation-mechanism comparison (part b/d of the user's goal)

Four mechanisms considered, each re-verified this session where possible:

| Mechanism | License safety | Reproducibility/pinning | Offline behavior | Update path | New bootstrap prereq? |
|---|---|---|---|---|---|
| **(a) Vendor files into this repo** | Requires per-item NOTICE/attribution (blocked today — no root LICENSE/NOTICE exists per the memo's §4, reconfirmed: `fd -H -t f 'LICENSE\|NOTICE' .` at repo root returns nothing) | Perfect — byte-pinned in this repo's own git history | Perfect — no network at use-time | Manual re-pull per update, reviewed like any PR | No |
| **(b) mise task running `npx skills add <source> -g -a claude-code -y`** | Inherits whatever the upstream repo's own license is at fetch time — no local review gate | **None** — confirmed no version/ref/sha pinning in `npx skills`' documented interface (memo's finding, unchanged); an unpinned auto-syncing fetch directly conflicts with this repo's `locked = true` / "never accept ambient provenance" doctrine (`AGENTS.md`) | Fails offline entirely | `npx skills update` exists but is itself unpinned | Yes — adds a live npx/network dependency to what is currently a fully offline-capable install |
| **(c) Claude Code plugin `dependencies` field (cross-plugin)** | Depends entirely on the depended-upon plugin's own marketplace/license — same review burden as (a) but deferred to install time | **Real semver-range pinning exists** (`~2.1.0` etc.) via the documented `dependencies` array in `plugin.json`, confirmed from official docs this session. **But cross-marketplace dependencies are blocked by default** — the depending marketplace's `marketplace.json` must explicitly list the target marketplace in `allowCrossMarketplaceDependenciesOn`, or install fails with a `cross-marketplace` error (confirmed from official docs + a live GitHub issue, `anthropics/claude-code#49620`, showing this exact failure mode reported by another user this year). Also confirmed via a second GitHub issue that the docs/implementation gap here has been actively evolving (`#48864`, marked resolved). This mechanism is real but **Claude-only** — it does nothing for Codex/Gemini/OpenCode, so it cannot be the sole answer for a cross-host bundle. | Only offline once installed; initial resolution requires network + the target marketplace already being trusted/added | Automatic on Claude Code's background plugin auto-update, or `/reload-plugins` | No new tool, but does add "must pre-approve a marketplace's `allowCrossMarketplaceDependenciesOn`" as new operator action |
| **(d) Fetch script with pinned commit SHAs** | Full control — script can enforce "must have a discoverable LICENSE at the pinned SHA before proceeding" | Perfect if implemented (SHA pin per source) | Fails offline unless combined with (a) as a cache | Bump SHA in the script, reviewed like any commit | Only if it introduces a new runtime (a Python/Node fetch script under `uv run` adds nothing new since the toolchain already runs Python via mise/uv) |

**Recommendation, reaffirming the existing memo with one addition:** **Primary = (a) vendor into this repo** (as the memo's §1 backlog already assumes for every item it doesn't explicitly skip), gated by first landing the root `LICENSE`/`THIRD-PARTY-NOTICES.md` the memo's §4 already specifies as a hard prerequisite. **Fallback = (d) a small fetch script with pinned SHAs**, used only for content genuinely too large/volatile to vendor wholesale (e.g., if someone eventually wants a slice of ECC's 281-skill catalog beyond what's been individually vetted) — this session found no reason to prefer (b) or (c) as primary: (b) fails this repo's own no-ambient-provenance doctrine outright, and (c) is real infrastructure but Claude-only and requires an operator-approved cross-marketplace allowlist entry that doesn't exist for any of hyperresearch/ECC/mattpocock today (none of them are on `known_marketplaces.json` in this environment — confirmed empty grep). (c) is worth using **later**, once/if this bundle wants to formally depend on `mattpocock-skills` specifically for the ~2 skills that don't collide and don't need setup coupling (none identified in this session — every mattpocock skill checked either collides by name or requires `/setup-matt-pocock-skills` coupling) — but it is not a general solution for "pull third-party skills in," only for a single already-vetted, already-in-official-marketplace dependency.

**Proposed namespacing rule (reaffirms and slightly extends the existing memo's fact-0c conclusion):** vendored third-party content must never land as a top-level `skills/<upstream-name>/` in this repo. Two sanctioned destinations only: (1) content that's genuinely a *reference/doctrine* extraction goes into `skills/agentic-sdlc/references/<topic>.md` (as the memo's backlog already does for TDD, debugging, code-review, merge-conflicts); (2) content that's a genuinely new, non-colliding, freestanding capability gets a **prefixed** directory name — e.g. `skills/sdlc-<capability>/` or another short project-specific prefix — so it can never collide with an upstream author's own unprefixed name on any host machine, present or future. This also sidesteps the entire ECC-281-name collision-sweep problem: nothing this repo vendors would ever be named identically to an ECC/mattpocock/hyperresearch skill in the first place, because nothing this repo vendors keeps the upstream's bare name.
