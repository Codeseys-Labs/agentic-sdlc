## (1) The three most consequential gaps in this domain

**Gap 1 — No receipt-vouching-shaped defense against a *partial-membership* forged receipt in the activation-planner.** pi-lab's `receipt-vouch.ts` exists specifically because two concrete exploits were reproduced against the shipped `dist/cli.js`: a forged receipt naming only the one entry an attacker wants removed, which "vouches" successfully because payload *membership* checking alone cannot distinguish "pi-lab put this here" from "the attacker's crafted claim happens to name something in the current payload." agentic-sdlc's activation-planner binds digests tightly (`manifest_sha256`, `plan_digest`, `operation_digest`, single-use grants) and has adversarial tests for symlink swaps, forged-root anchors, and substituted stages (17 tests matching `forg|substitut|symlink` in `tests/test_activation_transaction.py`) — but none of those tests are shaped like pi-lab's *specific* exploit class: a receipt/record that is internally well-formed and digest-consistent, yet dishonestly claims partial correspondence to a manifest that has since gained or lost entries. Because agentic-sdlc's activation model is single-path-per-operation (one `entry.path` per operation, with `owners` collision detection at `status_command`, confirmed reading lines 2900-2920), the *shape* of pi-lab's multi-key-partial-claim exploit may not be directly reachable today — but that absence has not been demonstrated by a test, only inferred by architecture. **Smallest closing change:** port pi-lab's `vouchReceipt`/`payload-entry-unaccounted` completeness check as an explicit test in `tests/test_activation_transaction.py` that constructs a receipt/commit record claiming a manifest whose entry set has since changed, and assert the tool refuses rather than silently accepting a subset-claiming record — even if the current architecture makes it currently unreachable, the test would document that the property is verified rather than assumed.

**Gap 2 — betterleaks pinned but not gated: the secrets scan is not in the dependency chain of `mise run check` and not wired into either lefthook hook.** Verified live: `mise.toml:98-100` shows `[tasks.check]` `depends = ["validate", "test", "self-test"]` with no betterleaks/secrets step; `lefthook.yml` (read in full) wires only `validate` (pre-commit) and `test`+`self-test` (pre-push); `skills/repo-toolchain-gates/SKILL.md:97` states outright "Wiring status in THIS bundle: version-pinned, invocation advisory / opt-in." This is self-disclosed, not hidden — but it means the repository's own secrets scanner has never actually screened a commit or push in this repo's own gate flow. pi-lab's ADR-0006 shows the concrete cost of skipping this: a real drifted-scanner-identity incident that silently passed for a period before being caught. **Smallest closing change:** add a `secrets` task to `mise.toml` invoking `betterleaks dir .` (or `git .` for full history on release branches) and add it to `[tasks.check]`'s `depends` list, or explicitly split it into a separate pre-push-only lefthook command — either way turning "advisory/opt-in" into "wired," which is a two-line mise.toml change plus one lefthook.yml line, not a new subsystem.

**Gap 3 — No secrets-scanner *artifact identity* qualification layer (digest-pin-and-verify-before-invoke), only install-time checksum verification.** agentic-sdlc trusts mise's install-time checksum (`mise.lock:150-171`, confirmed) to guarantee the binary that gets installed matches the pin, but has no equivalent to pi-lab's ADR-0006 runtime re-qualification: resolving the executable by absolute path with no shell/`which` indirection, digesting its bytes and proving its version by spawning it *at scan time*, and refusing with a distinct exit code (78 for identity mismatch, 75 for timeout, both distinct from clean=0/findings=1) before the scanner ever runs. This closes a real historical incident pi-lab suffered (Homebrew's ambient PATH resolving a different, unreviewed version than the one mise pinned, silently passing). Since agentic-sdlc's advisory invocation posture (Gap 2) means the scanner rarely runs today, this second-order gap is currently lower-stakes than Gap 2 — but if Gap 2 is closed without also closing Gap 3, the newly-wired gate would be exposed to exactly the failure mode pi-lab already reproduced and fixed. **Smallest closing change:** when closing Gap 2, wrap the `betterleaks` invocation in a thin qualification script (a Python analog of `secrets-gate.ts`) that resolves the exact executable path mise installed, re-hashes it against the `mise.lock`-recorded checksum, and refuses distinctly before scanning — this can reuse the existing `gate_receipt.py` self-hashing infrastructure almost verbatim rather than inventing new machinery.

## (2) Original inventions in agentic-sdlc — not prescribed by any source, not built by pi-lab

- **Single-use, expiring procedural grants (`GRANT_SCHEMA = "agentic-sdlc/procedural-grant@1"`) as the human-authorization primitive gating apply/recover.** No source memo names this pattern explicitly, and pi-lab's authorization primitive for the analogous action (uninstall reversal of a superseded payload) is a human-typed digest acknowledgement flag (`--acknowledge-payload-change=<digest>`), not a consumable token file with its own replay-refusal test. This is **load-bearing**: `test_grant_replay_and_expiry_are_refused` (verified reading the test) proves the mechanism actually blocks a second use of the same grant, which is a stronger authorization primitive than pi-lab's acknowledgement flag (which has no "already consumed" state — an operator could in principle re-supply the same `--acknowledge-payload-change` digest twice against two different receipts, since it's just a string comparison, not a consumed-token check). Given that the whole activation-transaction engine's authorization story rests on this primitive, it is a genuine, load-bearing original contribution — not speculative.

- **The `approval_authenticated: False` hard-pinned field baked into every terminal schema (commit/rollback/receipt/audit).** No source prescribes this specific pattern (a schema field whose value is contractually fixed to `False` and mechanically validated to be exactly that, so a terminal record can never assert human approval it never obtained). This is a small but genuinely clever invention: it makes "this activation record does not itself constitute authorization" a *type-level* fact rather than a documentation claim. Load-bearing in a narrow sense — it is exactly the kind of one-field control that closes a specific overclaim vector (a forged or careless terminal record asserting it was human-approved) cheaply. Speculative in a broader sense — since no code path ever *sets* this to `True` (there is no code that performs the authorization and flips the field), its practical value today is limited to "this record cannot claim what it's structurally forbidden from claiming," which is real but narrow.

- **`gate_receipt.py`'s general-purpose, arbitrary-command gate receipt (self-hashing, argv-binding, toolchain-digest-binding).** pi-lab's closest analog (ADR-0006's scanner-identity attestation) is scoped to exactly one tool's identity; agentic-sdlc's gate-receipt is a generic wrapper that could, in principle, receipt *any* gate command's argv/exit/toolchain-pin state. This generality is speculative rather than load-bearing today: `[tasks.check]` doesn't invoke `gate_receipt.py` to wrap itself (confirmed: `mise.toml:98-100` shows a plain `depends` list, no receipt-wrapping), so the mechanism exists as tested library code (`tests/test_gate_receipts.py`) without yet being wired into the actual gate task that would make it load-bearing.
