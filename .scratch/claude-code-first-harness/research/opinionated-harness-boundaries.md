# Opinionated agent harness boundary research

## Question and gated decision

**Question.** How do gstack, oh-my-opencode, oh-my-pi, and Everything Claude Code define their product boundaries across installation, ownership, configuration, skills/agents, model routing, orchestration, safety, updates, and the minimum successful user journey?

**Decision gated.** Define the scope and non-goals of a Claude-Code-first harness for Agentic SDLC without accidentally adopting a foreign library's ownership model or runtime plane.

**Research date and source policy.** 2026-08-14. This note uses repository-owned README files, manifests, scripts, and official project documentation only. “Verified” means directly stated or implemented in that source; “inferred” is marked as such.

## BLUF

Build the Claude-Code-first harness as a **narrow lifecycle-and-workflow layer**, not a replacement coding-agent runtime or a broad foreign-library installer. The four comparators converge on a useful user experience—install once, run one recognizable first workflow, then offer stronger orchestration—but divide sharply on ownership and safety. The strongest pattern to adapt is ECC's declared install state and single-path warning, paired with its explicit user/project/local scope and preflight direction. The strongest orchestration pattern is ECC's separation of interactive approval gates from background fan-out. The strongest technical pattern is OMP's recording of concrete provider/model identity, not merely a requested preference.

Deliberately reject gstack-style automatic session updates that alter a shared experience without a reviewed release/receipt, OMO's optional installer path to unattended full permissions, OMP's position as a replacement agent runtime with cross-harness configuration ingestion, and any default-on telemetry. Never take ownership of pre-existing user configuration merely because the harness can detect it.

**Confidence: high** for documented surface and lifecycle boundaries; **medium** for the recommendation, which is an inference from those boundaries and this repository's existing no-vendoring/explicit-lifecycle policy.

## Implications for the Claude-Code-first harness

### Adapt

1. **Make the lifecycle a product boundary.** Adopt ECC's single chosen install path, explicit scope, preflight/dry-run, and recorded ownership; retain only verifiably owned paths on repair or uninstall. This reinforces the bundle's present opt-in/no-adoption doctrine. [inferred from ECC evidence above]
2. **Make the first journey one small workflow.** gstack's short “install → office hours” and ECC's “install → plan → TDD/review” make the product legible. Start with a read-only planning/research command and one clearly named delivery workflow—not a catalog dump. [inferred]
3. **Separate orchestration from authority.** Use ECC's pattern: background workers may gather/review/verify, while approval to write a queue, commit, merge, deploy, or change user configuration remains in the interactive conductor. A failed or incomplete reviewer must not collapse to approval. [verified design evidence: [ECC workflow](https://github.com/affaan-m/everything-claude-code/blob/c9de8f5b2b3a225bca9befa2b7700aa5e3a4d1b8/workflows/README.md#L28-L63); recommendation inferred]
4. **Record effective runtime identity.** OMP's concrete provider/model transcript record is the right evidentiary concept. Preserve the existing distinction between requested route and verified readback; do not turn a role's preferred tier into claimed execution identity. [inferred from [OMP model identity](https://github.com/can1357/oh-my-pi/blob/ffd53ff92a6f575d499730475a73460dd7cc2eea/docs/models.md#L145-L165)]
5. **Offer bounded, opt-in safety profiles.** Borrow ECC's visible profiles and OMP's capability to actually block tool calls, but define enforcement claims precisely and test them. Do not describe advisory prompt text as a hard control. [inferred]

### Deliberately reject

1. **Do not become a replacement coding-agent runtime.** OMP's own terminal, tool protocol, provider stack, inherited host configuration, and state store are valuable for OMP, but would duplicate Claude Code rather than harness it. [inferred]
2. **Do not silently mutate or auto-update user/project configuration.** gstack's team flow combines SessionStart update behavior with repo bootstrap/commit instructions; the harness should instead require an explicit reviewed lifecycle command and preserve unrelated state. [inferred from verified gstack evidence]
3. **Do not sell or default to an unattended permission bypass.** OMO documents `approval_policy = "never"`, danger-full-access, and network enabled as an installer option. This product must keep any unsafe permission profile explicit, separate, and visibly forwarded, never a recommended default. [inferred from [OMO install guide](https://github.com/code-yeongyu/oh-my-opencode/blob/038ed0cbbefe2b40677b63867aeea0d16bc303e0/docs/guide/installation.md#L42-L52)]
4. **Do not bake provider subscriptions or static role-to-model chains into product identity.** OMO's value proposition includes these choices; a Claude-Code-first harness should instead dispatch only after a conductor-supplied certified runtime assignment and verified receipt. [inferred]
5. **Do not enable telemetry, marketplace acquisition, MCPs, or external-library installation as a side effect.** OMO telemetry defaults on, while ECC intentionally leaves bundled MCPs disabled in its Claude plugin path. Follow the latter boundary and make egress/installation explicit. [verified: [OMO telemetry](https://github.com/code-yeongyu/oh-my-opencode/blob/038ed0cbbefe2b40677b63867aeea0d16bc303e0/README.md#L215-L226), [ECC MCP boundary](https://github.com/affaan-m/everything-claude-code/blob/c9de8f5b2b3a225bca9befa2b7700aa5e3a4d1b8/README.md#L435-L445); recommendation inferred]

## Contradictions, open risks, and decision

- **gstack safety wording is internally inconsistent.** Its feature table calls `/freeze` a “hard block,” but its conventions call all safety skills inline advisory prose. Treat this as non-load-bearing inspiration until an implementation-level enforcement test proves scope blocking. [verified contradiction]
- **OMO naming is in transition.** Package, repository path, legacy config filenames, and product branding do not line up. Any integration proposal must bind to a specific canonical repository/commit and install channel, not the phrase “oh-my-opencode.” [verified]
- **ECC's current-versus-planned install surfaces are easy to confuse.** The 2.2 package wizard is documented but unavailable in current npm 2.1.0; do not cite it as a working canary. [verified]
- **No external runtime was installed or exercised.** This is source-based boundary research, not a compatibility/security test. The cheapest decisive follow-up, only if adoption is proposed, is an isolated temporary-home install dry-run plus a before/after filesystem/config diff for the named adapter.

**Decision.** Proceed with a Claude-Code-first harness that owns only its explicit state and links, keeps agentic workflow methodology in host-agnostic skills, requires preflight plus user confirmation for configuration changes, records runtime receipt evidence, and reserves irreversible/external actions to the conductor. Do not adopt any comparator as a bundled dependency or model-routing authority.
